## 1. Context

Greenfield, standalone, self-serve on-call rotation tracker for teams of 3-15, replacing pinned Slack messages and spreadsheets.
It answers "who is on-call now" in seconds (timezone-localized, plus an unauthenticated shared read-only link), auto-advances a recurring rotation with date-scoped overrides and two-party swaps, and notifies the incoming on-call by SMS and email with acknowledgment, timeout escalation to a secondary, and voice as an added layer.
Per-notification delivery status is visible to leads so the tool never fails silently.

In scope: one rotation per team, one escalation tier, responsive web, passwordless auth, SMS + email (Must), voice escalation (Should), delivery-status logging, consent-gated analytics.
Out of scope: incident management, Slack-bot-as-primary, SSO/RBAC/audit, follow-the-sun escalation, native mobile, multi-region scheduling for 500+ engineer orgs, push, billing.

### 1.1 Context diagram (nodes and edges, described)

Nodes: **Browser (authenticated)**; **Browser (anonymous)** (shared link, no session); **Web application** (server-rendered app plus JSON API, one deployable holding all 3.1 modules); **PostgreSQL** (teams, members, rotations, overrides, swaps, notifications, escalations, consents); **Job runner** (in-process, durable queue in that same PostgreSQL); **Read cache** (CDN/edge plus app cache for the shared-link payload); **Telephony provider** (Twilio or equivalent, D-01); **Email provider** (`Placeholder: vendor TBD`); **Managed cloud KMS**; **Analytics platform** (`Assumption: PostHog or equivalent, D-08 TBD`); **Observability backend** (`Placeholder: vendor TBD`, Question 6); **Out-of-band watchdog** (external dead-man's-switch and alert channel, deliberately not this system and not its region, `Placeholder: vendor TBD`).

Edges: authenticated browser -> web app, HTTPS (TLS 1.2+) with a passwordless session cookie; anonymous browser -> read cache -> web app, HTTPS GET only with a 128-bit share token (ADR-005); web app <-> PostgreSQL, TCP/TLS SQL; web app -> job runner by SQL insert inside the triggering write's transaction; job runner -> telephony and email providers, HTTPS REST, retried; both providers -> web app, signed webhooks carrying delivery status and voice/DTMF acknowledgment; web app -> KMS, data-key wrap/unwrap only (contact plaintext never leaves the app); browser -> analytics only after consent; web app and job runner -> observability backend; job runner -> watchdog heartbeat, and watchdog -> pager owner when that heartbeat stops.
No provider internals are assumed beyond the public contract in the brief.

## 2. Architecture Characteristics Scorecard

## 3. Component Design

### 3.1 Components

| Component | Responsibility | Owns data | Talks to |
|---|---|---|---|
| Identity & Session | Passwordless auth (ADR-011), sessions, membership checks | `users`, `sessions`, `login_tokens` | Email/Telephony providers, PostgreSQL |
| Team & Membership | Team CRUD, members, contact details, secondary contact, per-team escalation timeout | `teams`, `members`, `contact_methods` (encrypted) | KMS, PostgreSQL |
| Schedule Engine | RRULE expansion into materialized instances, override and swap precedence, holder resolution, DST handling | `rotations`, `shift_instances`, `overrides`, `swaps` | RRULE library, PostgreSQL |
| Read Model / Current-On-Call API | Authenticated rotation view and anonymous shared-link payload; owns cache contract, staleness stamp, token lifecycle | `share_links`; reads `shift_instances` | Schedule Engine, Read cache, PostgreSQL |
| Notification Orchestrator | What to send and when, per-channel fan-out, per-notification idempotency | `notifications`, `notification_attempts` | Job runner, Channel Adapters, PostgreSQL |
| Channel Adapters (SMS/Voice/Email) | Provider sends, signature-verified webhook ingestion, status normalization, per-provider circuit breakers | `provider_events` (raw payload) | Telephony and Email providers |
| Escalation Controller | Acknowledgment timer, escalation to secondary, voice layer, escalation event log | `escalations`, `acknowledgments` | Orchestrator, Job runner, PostgreSQL |
| Delivery Log UI | Lead-facing per-notification status; the surface behind the self-diagnosis target | none (read-only) | Orchestrator, Escalation Controller |
| Consent & Privacy | Consent capture/revocation, analytics gating, 30-day deletion for removed members | `consents`, `deletion_jobs` | Analytics platform, Job runner |
| Job Runner | Durable scheduled and delayed execution, retry/backoff, per-queue concurrency limits, dead-lettering, liveness heartbeat | `jobs`, `dead_letter_jobs`, `runner_heartbeat` | All of the above, PostgreSQL, watchdog |

### 3.2 Architectural style

**Modular monolith with an embedded durable job runner: one deployable on a managed platform over one PostgreSQL instance.** Chosen against the scorecard, not by default:

- *Simplicity (High)* dominates: 2-3 engineers, no SRE, one quarter, a per-team cost ceiling. Microservices add partitions, distributed tracing, and per-service deploys this team cannot operate and this price point cannot fund.
- *Correctness (High)* wants one transactional boundary: override precedence, swap application, materialization, and notification enqueue commit together, eliminating the "schedule changed but the notifier never heard" bug class that would otherwise need sagas or an outbox.
- *Reliability (High)* is bought with durability rather than service redundancy: jobs are rows, so a crash loses nothing and a restarted process resumes.
- The cost is *blast-radius isolation*: a pathological query or notification storm shares CPU and connections with everything else. Addressed by in-process bulkheads (separate pools, bounded per-queue concurrency), not separate processes, and accepted explicitly.

Module boundaries are enforced in code (narrow interfaces, no cross-module table access) so the notifier or schedule engine can be extracted later. Extractability is the hedge; extraction is not planned for v1.

**Ownership and operations.** The design assumes one named pager owner (`Placeholder: owner TBD`) plus a documented backup, not a rotation, at pilot scale; that person is paged by the out-of-band watchdog, never by this tool (ADR-013).
The runbook ADR-001 claims must exist before pilot start and must cover: dead or stalled job runner, dead-letter replay, telephony breaker open, KMS breaker open, forced share-link cache purge, restore-from-PITR (ADR-015), materialization-horizon alert, stalled `deletion_jobs`.
Until it exists the Simplicity target is unmet, tracked as a Section 6 risk rather than assumed.

### 3.3 Data flow

**Flow A - shift start and acknowledgment (safety-critical).** The Schedule Engine materializes instances over a rolling forward window (`Assumption: 90 days`), recomputed inside the same transaction as any rotation, override, or swap write.
Materialization enqueues a `notify_shift_start` job with a run-at time and an idempotency key on `(shift_instance_id, boundary_instant)`; keying on the absolute instant rather than wall-clock is what satisfies R-03/R-15, since a DST fall-back repeated hour cannot produce a second job.
At run time the Orchestrator creates one `notification` and fans out to SMS and email concurrently - both channels every time, email co-equal rather than a fallback.
Webhooks update `notification_attempts` with normalized status plus raw payload, idempotent on provider message ID since providers redeliver.
The Escalation Controller schedules `escalation_check` at `now + team.escalation_timeout` (per-team, default 10 min); absent an acknowledgment it notifies the secondary and, when the voice flag is on, places a call, writing an `escalations` row at each step whether or not it succeeds.
Acknowledgment arrives by authenticated click, inbound SMS, or voice DTMF; first wins, later ones are recorded only.

**Failure paths.**

- *Telephony call fails*: exponential backoff with jitter, capped at 2 consecutive attempts (D-01), then mark the attempt failed, rely on email, record `channel_failed_over` - a visible degradation, never a silent one.
- *Telephony fully down*: an adapter circuit breaker opens at `Estimate: >=50% failures across the trailing 20 calls, minimum 10 calls in a 60s window`, half-open probe after 30s, closing on one success - concrete so it is testable at launch rather than tuned in production. It fails fast into email instead of burning the queue on timeouts. Breaker state is alertable; it is a fast local control, distinct from the slower hour-long >5% delivery-failure rollback trigger.
- *KMS unavailable*: per-tenant data keys sit in an in-memory cache (`Assumption: 15 min TTL`; plaintext contact data is never cached to widen it - a deliberate security-over-availability choice). Cache hits proceed unaffected. On a miss during an outage a breaker opens after 3 consecutive failures; the send retries with backoff for up to `team.escalation_timeout`, then writes the notification as `blocked_kms`, records an escalation row, shows the block in the Delivery Log, and pages via the watchdog. This is the one dependency that cannot degrade gracefully, and it is named as such rather than hidden.
- *Poison or repeatedly failing job*: max-attempt cap per job class (`Assumption: 5`, or 2 for telephony sends per D-01). On exhaustion the row moves to `dead_letter_jobs` with its last error rather than retrying forever or vanishing. Dead-lettered notification, escalation, or `deletion_jobs` rows page immediately; other classes produce a daily digest. Replay is a runbook step.
- *Job runner dead or stalled*: the runner writes `runner_heartbeat` every 30s. An out-of-band watchdog, hosted outside this system and its region, pages when the heartbeat is older than 3 minutes or a ready job has been due more than 2 minutes. This is the only alert path that must not depend on the app, its database, or its region, precisely because a silently stopped runner is the exact failure the product exists to prevent.
- *Webhook never arrives*: the escalation timer is the backstop - absence of positive delivery status counts as non-acknowledgment, so a lost webhook escalates rather than stalls.
- *Email down*: SMS remains; if both are down the escalation event is still written and surfaced. The contract is that failure is always recorded, not that delivery is guaranteed.
- *Job backlog*: per-queue concurrency limits bulkhead low-priority work (analytics deletion, cache warming) away from `notify_shift_start`, which has a dedicated reserved queue.
- *Database unavailable*: writes fail closed with a clear error; the anonymous read path serves the cached payload with a stale banner, except for links with no warm entry, which fail outright (ADR-005).
- *Read cache unavailable*: the shared link falls back to read-through against the origin - correct but slower, losing the 3G latency budget and the outage-survival property, not the answer. Cache down plus origin down is a hard failure, accepted at this price point.
- *Cache invalidation fails*: invalidation is best-effort, so staleness is bounded by the 60s TTL rather than permanent; forced purge is a runbook step, and payloads carry a schema-version key so a shape change cannot serve an old structure indefinitely.
- *Deletion queue stalls*: any `deletion_jobs` row older than 7 days pages, giving 23 days of margin on R-17. A silent stall here is a compliance breach, so it gets the same alert class as the materialization horizon.
- *Dogfood circularity*: the team pages itself through this tool (11.1), so an outage of the tool is an outage of its own paging path. Mitigated for operators by the watchdog, for users by a documented static contact list held outside the system; tracked as a risk rather than solved.

**Flow B - anonymous shared link.** GET with a 128-bit share token hits the cache; on hit, cached payload plus "as of" stamp; on miss, resolve the holder from `shift_instances` and repopulate. The payload is deliberately minimal so it stays cacheable and leaks nothing beyond the holder's display name and a coarse handoff time.

**Flow C - rotation edit.** Authenticated write -> validate invariants -> apply override/swap -> recompute the forward window -> reconcile jobs (cancel removed, enqueue new) -> invalidate the shared-link cache key. All in one transaction except invalidation, which is best-effort and bounded by TTL.

### 3.4 Consistency and distribution trade-offs

The core is intentionally not distributed: Schedule Engine, Orchestrator, Escalation Controller, and Job Runner share one PostgreSQL instance. Every distributed interaction, internal and external, takes a position below.

| Interaction | Position | Why, and what it costs |
|---|---|---|
| App modules -> PostgreSQL (core) | **CP, single-node** | Strong consistency by construction is the main reason for the style in 3.2; a stale or divergent schedule is worse than a refused write. The price is real: a single node is not partition-tolerant, so a database failure is a total write outage with no quorum. RPO/RTO and restore in ADR-015 |
| Anonymous shared-link read | **AP** | R-04/7.3 require last-known cached state with a stale banner rather than an error. Bounded staleness (`Assumption: 60s TTL plus write invalidation`) beats unavailability on a surface likely opened during an outage; the as-of stamp makes staleness visible. Costs: up to 60s behind, and a cold entry gets no availability benefit at all |
| App -> Telephony provider | **AP** | Outside our consistency domain: a timed-out send has unknown outcome, so we accept at-least-once and reconcile via webhooks and idempotency keys rather than blocking (ADR-010). Cost: duplicate SMS |
| App -> Email provider | **AP** | Same reasoning and cost, stated separately because ADR-004 makes email a co-equal Must channel on the safety-critical path, not a lesser leg: a timed-out email is retried without knowing the first outcome, so duplicate emails are accepted too |
| App -> KMS | **CP-dependent (fail-closed)** | AP is not available: without a data key the plaintext does not exist, so there is no degraded-but-useful answer. We fail closed rather than store decrypted contacts to stay available. Cost: KMS availability is a hard ceiling on notification availability, softened only by the 15-minute key cache, itself a security-for-availability trade |
| Webhook -> notification state | **AP, eventually consistent** | Provider callbacks arrive seconds to minutes late or out of order, so blocking a send on terminal status would add unbounded latency to a 15-minute budget, and polling reconciliation would cost an API call per attempt for a state the escalation timer already backstops. Unknown status is treated as non-acknowledgment, which is what actually protects the user. Cost: the Delivery Log can show `pending` for a delivered message, which looks like a bug and must be labelled in the UI |
| Authenticated rotation view | **CP** | Reads the datastore directly, uncached; a lead editing must see true state immediately, and 2s p95 is affordable uncached at this scale. Cost: this surface goes down with the database |
| App -> Analytics platform | **AP, lossy by design** | Fire-and-forget and consent-gated. Losing an analytics event is acceptable; losing a notification record is not, hence separate stores |

## 4. Architecture Decision Records

ADR numbers are permanent and never reused. `Deciders` is a placeholder throughout because the brief names no individuals; it must be filled before any ADR moves from Proposed to Accepted. All statuses: Proposed, 2026-07-27.

### ADR-001: Modular monolith with an embedded durable job runner

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: sustained load beyond 200 teams, or a second engineering team taking ownership of the notifier.
**Context**: Serves Simplicity, Correctness, and Reliability (all High) under 2-3 engineers with no SRE, ~one quarter to GA, per-team cost well below $50-100/month, ceiling ~200 teams / ~3,000 members.
**Decision**: Build one deployable modular monolith with enforced internal module boundaries and an embedded durable job runner rather than separate services.
**Alternatives considered**: (a) Microservices splitting scheduler, notifier, read API - rejected: creates cross-service consistency problems in exactly the schedule-to-notification handoff that must never drift, and demands operational maturity this team lacks. (b) Serverless plus a managed queue - rejected: escalation timers and materialization are long-lived, ordered, stateful concerns, and cold starts threaten the 200ms skeleton budget.
**Consequences**: Easier - one transaction across schedule and notification state, one deploy, one runbook (3.2, not yet written), cheap at target scale, whole-flow local testability. Harder - no blast-radius isolation between read path and notifier (mitigated by bulkheads, not eliminated); the app scales as one unit; a bad deploy affects everything at once, which matters more because core scheduling and display are not feature-flagged and rely on deployment-revert rollback, making the expand/contract discipline in Section 5 load-bearing rather than optional.

### ADR-002: PostgreSQL as the single primary datastore, including the job queue

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: queue throughput above `Estimate: 50 jobs/s sustained`, or notification-table size past the ADR-009 threshold after partitioning.
**Context**: Serves Correctness, Reliability, Observability, Simplicity (all High). Delivery-status records are product surface (the lead-facing Delivery Log), not disposable telemetry, so they need transactional queryable storage.
**Decision**: Use one PostgreSQL instance as system of record for scheduling, notification, escalation, and consent data, and back the job queue with the same database rather than adding a broker.
**Alternatives considered**: (a) Postgres plus Redis/SQS - rejected: splits the transaction boundary so enqueue is no longer atomic with the schedule write, reintroducing the outbox problem for marginal throughput at ~24,000 messages/month (~0.01/s average). (b) Document store - rejected: override precedence and holder resolution are relational, constraint-heavy queries where foreign keys and transactions are the point. (c) Separate log store for delivery status - rejected, see ADR-009.
**Consequences**: Easier - atomic schedule-plus-notification writes, one thing to monitor, exactly-once *job scheduling* via unique idempotency keys. That guarantee is scoped strictly to enqueue: the side effect (a provider send) is still at-least-once per ADR-010, so it neither contradicts the Section 2 trade-off nor buys anything on the delivery side. Harder - the database is a SPOF and the scaling bottleneck (Section 6 risk, RPO/RTO in ADR-015); queue polling adds baseline load; notification tables dominate growth. Low reversibility, see Section 5.

### ADR-003: Materialized shift instances instead of on-demand RRULE evaluation

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: Question 4 answered in favour of a long forward view on the shared link, or per-member timezones entering scope (ADR-012).
**Context**: Serves Correctness (High), where the brief states a wrong answer is worse than no tool, and Reliability (High). D-04 mandates an established RRULE/iCal library, leaving only holder resolution, override precedence, and DST handling custom.
**Decision**: Expand the RRULE into concrete `shift_instances` rows over a rolling forward window (`Assumption: 90 days`) at write time, and resolve both the current holder and every notification from those rows.
**Alternatives considered**: (a) Evaluate the RRULE on every read and send - rejected: read path and notifier would compute independently, so a library or tzdata change could make them disagree, and DST correctness would need re-proving at every call site. (b) Materialize to a fixed end date - rejected: rotations are open-ended, so row count would be unbounded. (c) Materialize per member in the member's own timezone - rejected for v1 and recorded as ADR-012 because it is a product-visible limitation, not just an implementation choice.
**Consequences**: Easier - one authoritative answer for display and notification; DST becomes a testable property of one function against a frozen clock; overrides and swaps are row-level edits; iCal export (R-11) becomes straightforward. Harder - every edit triggers recompute-and-reconcile of pending jobs, real write-path complexity and a genuine bug source; a background job must keep extending the horizon, and if it stalls, shifts silently stop existing beyond it, which is why the horizon alert in Section 6 exists.

### ADR-004: Always send SMS and email in parallel, with an explicit failover event

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: per-member channel preference entering scope, or telephony spend approaching the $15/team/month guardrail.
**Context**: Serves Reliability and Observability (High). D-01 mandates a single telephony provider with email fallback after 2 consecutive failures and defers multi-provider abstraction post-pilot. A2P 10DLC registration (D-02, 1-4 weeks) gates production SMS and may miss 2026-09-07.
**Decision**: Send both SMS and email concurrently for every shift-start notification rather than treating email as a post-failure fallback, recording a distinct `channel_failed_over` event whenever the telephony path degrades.
**Alternatives considered**: (a) SMS-first with email only after 2 failures, the literal D-01 minimum - rejected: makes every notification depend on one vendor on the safety-critical path and adds the retry window to time-to-notify. (b) A second SMS provider - rejected: deferred post-pilot by D-01 and unaffordable within the $15/team/month guardrail.
**Consequences**: Easier - a full Twilio outage degrades to email-only rather than nothing; the 10DLC risk becomes a config change (email-only launch) rather than an architectural one; every degradation is a queryable event feeding the >5% rollback trigger. Harder - more notification noise per shift start, pulling per-member channel preference forward; two statuses per notification force the Delivery Log to express partial success rather than a single green check. Cost quantified: ~24,000 emails/month at the v1 ceiling, `Estimate: $0.0004 per transactional email`, roughly $10/month across 200 teams, about $0.05/team/month against a $15/team/month ceiling - a rounding error, unlike a second SMS provider at `Estimate: $0.0079/SMS`, which would roughly double the dominant cost line.

### ADR-005: Bounded-staleness cached read for the anonymous shared link (AP over CP)

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: Question 4 (holder only vs next 2-3 shifts), which changes payload cacheability.
**Context**: Serves Availability of the read path and Security and privacy (both High), since this is the only unauthenticated surface. R-04 makes the link a primary surface, 7.3 requires last-known cached state with a stale banner during an outage, and the floor is under 2s p95 on 3G with a 200ms skeleton.
**Decision**: Serve the shared-link payload from a cache with a short TTL (`Assumption: 60s`) plus write invalidation, always stamped with a visible "as of" timestamp, falling back to the last cached payload with a stale banner when the backend is unavailable, addressed by a 128-bit CSPRNG token.
**Access control specifics** (the only control on this path, so stated numerically rather than as "unguessable"): tokens are 128 bits from a CSPRNG per NIST SP 800-90A, base32url-encoded, stored only as a hash, revocable and regenerable per team from the UI, rate-limited per token and per source IP, served with `noindex`/`nofollow` and private edge scoping. There is no rotation schedule: rotation is user-initiated on suspected exposure, the accepted weakness of capability-URL access, which is why the payload carries only display name and coarse handoff time.
**Alternatives considered**: (a) Always read through to the database - rejected: makes the surface most likely to be opened during an outage fail exactly when needed, contradicting 7.3. (b) Long-lived static regeneration - rejected: a swap made minutes before an incident would not appear. (c) Lightweight auth on the shared link - rejected: R-04 exists precisely to be openable by someone with no account mid-incident.
**Consequences**: Easier - the read path survives an app or database outage for links already in cache, is cheap at low volume, and meets the 3G latency floor. Harder - a cold-cache hole: a link never fetched within the TTL window, or evicted, returns an error during an origin outage, so availability is best for frequently-viewed links and zero for a first-time viewer of a rare one. Partially mitigated by warming the payload on write for every active share link, trading a small write cost for a smaller hole; the hole is not closed. Also: viewers can be a TTL out of date; invalidation is best-effort; authenticated view and shared link can briefly disagree, generating support questions; a leaked URL is a leaked view until revoked.

### ADR-006: Per-team configurable escalation timeout, not a hard-coded default

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: Q6 answered on 2026-08-10.
**Context**: Serves Reliability of the escalation path (High). Q6 is blocking with a 2026-08-10 date and states the 10-minute default is a placeholder, so the acceptable timeout is genuinely unknown.
**Decision**: Store the acknowledgment timeout as a per-team column with a system default of 10 minutes, and derive every escalation timer from it at job-schedule time.
**Alternatives considered**: (a) Hard-code 10 minutes for v1 - rejected: changing it later requires rescheduling in-flight escalation jobs plus a migration, and the blocking question means the value will almost certainly change during pilot. (b) A global operator-tunable constant - rejected: pilot teams differ, and one value would force Q6's answer prematurely.
**Consequences**: Easier - Q6 answered empirically from pilot data; per-team tuning without a deploy. Harder - scheduled escalation jobs must be reconciled when a team changes its timeout, an extra reconciliation edge case. The Section 2 Reliability target is stated as `team.escalation_timeout + 5 min` precisely because of this: 15 minutes is the default-configuration case, a team choosing 20 minutes is held to 25, reporting must be per team, and any aggregate "99% within 15 minutes" claim is valid only across teams left on the default.

### ADR-007: Envelope encryption of contact data with a deterministic blind index

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: D-07 sign-off on 2026-08-21, or any requirement for partial-phone search.
**Context**: Serves Security and privacy (High): AES-256 at rest via managed KMS, TLS 1.2+, OWASP ASVS L1, no stored passwords (R-13), R-17 consent plus 30-day deletion. D-07 GDPR sign-off by 2026-08-21 gates any EU pilot team.
**Decision**: Encrypt phone numbers and email addresses at the column level with KMS envelope encryption using per-tenant data keys, with lookup via a deterministic keyed blind index over the normalized value (E.164 for phone, lowercased for email).
**Alternatives considered**: (a) Volume-level at-rest encryption only - rejected: no protection against application- or backup-level exposure and thin evidence for GDPR sign-off. (b) Application-held static key - rejected: puts key material in the deploy artifact and makes rotation manual and error-prone. (c) Tokenization inside the telephony vendor - rejected: deepens the single-vendor coupling D-01 already flags.
**Consequences**: Easier - a credible GDPR and ASVS L1 story; per-tenant key destruction is a clean deletion mechanism. Harder - encrypted columns cannot be searched, sorted, or partially matched, blocking future partial-phone lookup; blind-index key rotation requires full reindexing; every send costs a KMS decrypt, making KMS availability a hard ceiling on notification availability, with cache, breaker, and fail-closed behaviour in 3.3 and the CAP position in 3.4.

### ADR-008: Single-region, multi-tenant hosting with shared schema and row-level tenant scoping

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: D-07 sign-off on 2026-08-21, or the first customer with a written residency requirement.
**Context**: Serves Simplicity (High) and materially affects two other High characteristics rather than being cost-neutral: it puts Security and privacy at risk by making tenant isolation a query-layer property instead of a physical one, and it caps Availability of the read path, because one region hosts app, database, notifier, and cache origin. The brief flags hosting as absent from the PRD; EU residency is implied by D-07 but never written down.
**Decision**: Deploy a single-region multi-tenant instance with a shared schema and mandatory `team_id` scoping on every tenant-owned table, deferring region strategy until the D-07 sign-off states an actual residency requirement.
**Alternatives considered**: (a) Per-tenant database or schema - rejected: 200 tenants of 15 people does not justify the migration and operational fan-out for 2-3 engineers, though it would have made the isolation risk physical rather than logical. (b) Multi-region from day one - rejected as speculative, with a cost that breaks the per-team ceiling and an operational load 2-3 engineers with no SRE cannot carry.
**Consequences**: Easier - one database to operate, migrate, back up, monitor; cheapest path to pilot. Harder - a tenant-scoping bug is a cross-tenant leak, so scoping must be enforced structurally by a query layer that refuses unscoped tenant-table access rather than by developer discipline. Availability cost, stated because Section 2 ranks the read path High: a regional outage removes shared link, notifier, and cache origin simultaneously, so ADR-005's stale-cache fallback survives only app or database failure, and the 99.9% figure is a bet on the region's own availability. Accepted for pilot because a regional outage is also an outage of the incident the tool serves. If D-07 lands with EU residency, a second region is a significant unbudgeted change (Section 6 risk).

### ADR-009: Delivery status as first-class transactional product data, with dated retention

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: notification-row count above `Assumption: 50M`, or the retention decision landing on 2026-08-21.
**Context**: Serves Observability (High). The brief's whole premise is that the tool must never fail silently, and the Delivery Log is the surface that proves it.
**Decision**: Persist every attempt, provider callback, escalation, and acknowledgment as a queryable relational record in the primary datastore, joinable to teams, members, and shifts, with monthly partitioning from day one and default retention of `Assumption: 13 months` for attempt and callback rows.
**Alternatives considered**: (a) Ship delivery status to a log or metrics sink - rejected: the lead-facing log needs joins to product data and must be queryable after the fact by a non-engineer, which log sinks serve badly and metrics sinks not at all. (b) Status only as a denormalized column on `notifications` - rejected: destroys the per-attempt history that makes a missed page explainable. (c) Unbounded retention - rejected: these are the fastest-growing tables in the system.
**Consequences**: Easier - the self-diagnosis target becomes a product query rather than an ops investigation; the >5% rollback trigger reads the same rows. Harder - these tables dominate storage growth and query planning in the ADR-002 database; partitioning from day one costs schema complexity before it is needed; retention means a lead loses the ability to explain an incident older than the window, a real product limitation and not just a storage decision. The retention number is `Placeholder: owner TBD` to confirm by 2026-08-21; partitioning ships regardless so the decision stays a policy change, not a migration.

### ADR-010: At-least-once notification delivery, accepting duplicate pages

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: pilot feedback showing duplicate pages materially eroding trust.
**Context**: Serves Reliability (High). Provider sends can time out with an unknown outcome and webhooks arrive late or out of order (3.4), so some race between a retry and a late callback is unavoidable.
**Decision**: Guarantee at-least-once delivery per notification, deduplicating only what a single idempotency key can cover (job enqueue and provider-message-ID callback processing), and accept that a send retried after an ambiguous timeout may produce a duplicate SMS or email.
**Alternatives considered**: (a) A dedup window suppressing any second send within N minutes for the same `(member, shift_instance)` - rejected: it converts an ambiguous-outcome case into a possible missed page, since the suppressed send may be the only one that ever arrived; the asymmetry between duplicate and missed makes that a bad trade here. (b) Provider-side idempotency keys as a complete answer - rejected: coverage varies by provider and D-01's single vendor means no portable guarantee. (c) Two-phase confirm before sending - rejected: adds latency to a 15-minute budget for a guarantee the escalation timer already backstops.
**Consequences**: Easier - the send path never reasons about unknown outcomes; retries are always safe; no distributed dedup state. Harder - an engineer can receive the same page twice, user-visible noise that erodes trust if frequent; the Delivery Log must show multiple attempts for one logical notification without looking like a bug; the duplicate rate is unmeasured until pilot and should be reported.

### ADR-011: Passwordless authentication via emailed magic link, with SMS as a secondary path

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: any SSO requirement (out of scope), or measured auth-email deliverability below `Assumption: 99%`.
**Context**: Serves Security and privacy (High). R-13 forbids stored passwords, and the Section 2 trade-off concedes that passwordless puts email/SMS deliverability on the auth critical path.
**Decision**: Authenticate with a single-use, `Assumption: 15-minute`, device-bound magic link sent to the member's verified email, with an SMS one-time code as an alternate path when email is unavailable, and long-lived sessions (`Assumption: 30 days`) so routine use rarely re-authenticates.
**Alternatives considered**: (a) SMS OTP as primary - rejected: puts auth behind the same A2P 10DLC gate (D-02) that may miss 2026-09-07 and behind the single telephony vendor D-01 flags as a SPOF. (b) Email OTP code instead of a link - rejected as roughly equivalent in security but worse on mobile, though it is the cheapest substitution if corporate link-rewriting proves a problem. (c) Passwords with a breach-check - rejected outright by R-13.
**Consequences**: Easier - no password database, reset flow, or credential-stuffing surface; ASVS L1 comfortably met. Harder - a member is locked out whenever both email and SMS delivery fail, exactly the failure mode most likely during the incident when they need the tool, mitigated only by the 30-day session rather than a true offline path; email link-rewriting and prefetching by security appliances can consume a single-use link, so links must tolerate a HEAD/prefetch without burning; recovery reduces to a manual team-admin action (`Placeholder: process TBD`), a support cost at pilot scale and a real gap beyond it.

### ADR-012: One scheduling timezone per rotation in v1

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: the first distributed pilot team reporting a handoff-time complaint, or follow-the-sun entering scope.
**Context**: Serves Correctness (High). Display is always localized to the viewer; the question is only which timezone defines the handoff instant.
**Decision**: Each rotation carries exactly one scheduling timezone defining shift boundaries and DST behaviour; every member's view renders those instants in their own local time, but no member can shift the boundary for themselves.
**Alternatives considered**: (a) Per-member scheduling timezone - rejected for v1: makes "when does the shift start" ambiguous for a single shift instance, multiplies the DST test matrix R-03/R-15 depend on, and follow-the-sun is out of scope. (b) UTC-only scheduling - rejected: forces every team to reason about a timezone none of them lives in, and 09:00 local handoffs would drift by an hour twice a year.
**Consequences**: Easier - one boundary instant per shift, one DST test surface, one authoritative materialization (ADR-003). Harder - a distributed team gets a handoff at an awkward local hour for some members with no per-member adjustment; teams split across continents will feel this as a missing feature; adding per-member timezones later changes the `shift_instances` model and the notification key, so this is a schema-level commitment, not a UI setting.

### ADR-013: Operational alerting separate from product analytics, with out-of-band paging

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: Question 6 resolution, target 2026-08-21.
**Context**: Serves Observability and Reliability (High). The 11.5 rollback triggers are only real if something evaluates them automatically, and 11.1 dogfood circularity means alerting through this tool is alerting through the thing that is down.
**Decision**: Run operational alerting on a dedicated observability backend distinct from the D-08 product-analytics platform, and route every page for this system through an out-of-band channel (external watchdog plus a non-product paging path) sharing no infrastructure or region with the application.
**Alternatives considered**: (a) Reuse the analytics platform as alerting backend - rejected: consent-gated, fire-and-forget, client-side pipelines are lossy by design (3.4), and a rollback trigger that silently under-counts is worse than no trigger. (b) Page the owner through this tool - rejected: circular, and it fails exactly when needed. (c) Alert only via email - rejected: no acknowledgment, no escalation, same deliverability dependency as ADR-011.
**Consequences**: Easier - guardrail evaluation and rollback triggers become automatic and trustworthy; a full outage still produces a page. Harder - a second vendor, bill, and configuration surface against the Simplicity target; two places to look when investigating; the vendor is unchosen, so until Question 6 closes the Observability target is unverifiable and the 11.5 triggers are aspirational.

### ADR-014: Defer the language and runtime choice, constrained by library requirements

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: build commit, gated by Q8/Q9 on 2026-08-14. This ADR must close before that date.
**Context**: Serves Correctness (High), because the recurrence and timezone libraries carry the risk D-04 exists to contain. The brief names no language and this document should not invent one, but a Low-reversibility choice left open is a decision with a cost, not a neutral omission.
**Decision**: Do not name a runtime here; bind the choice to hard requirements - a mature, maintained RRULE/iCal implementation (D-04), a first-class IANA tzdata implementation with explicit DST-ambiguity handling, and concurrent HTTP with connection pooling - and require the building team to record the resolved choice as an ADR before build commit.
**Alternatives considered**: (a) Name a plausible runtime now - rejected: fabrication, and a Low-reversibility choice made without the team that maintains it is worse than one made late. (b) Leave the requirement unstated too - rejected: without the library constraints written down the deferral gives no guidance at all.
**Consequences**: Easier - the choice lands with the people who live with it, and the correctness-critical constraints are explicit. Harder, the real cost of deferral: the deploy pipeline, base image, resource profile, and concurrency model in Section 5 cannot be specified until it closes, so that row stays vaguer than it should; benchmarking against the 200ms and 2s budgets cannot start; and the longer it stays open, the more likely it is made under build-commit time pressure, which is exactly how Low-reversibility choices go wrong.

### ADR-015: Managed PostgreSQL with PITR, stated RPO/RTO, and rehearsed restore

**Deciders**: `Placeholder: TBD`. **Supersedes**: none. **Revisit trigger**: a failed restore rehearsal, or any customer commitment tighter than the stated RTO.
**Context**: Serves Reliability and Simplicity (High). ADR-002 makes one database the system of record and a SPOF; a CP single node (3.4) makes recovery procedure, not redundancy, the availability answer.
**Decision**: Use the platform's managed PostgreSQL with continuous WAL archiving and point-in-time recovery, targeting `Assumption: RPO 5 minutes` and `Assumption: RTO 1 hour`, with a restore rehearsal into a scratch environment before pilot start and quarterly after, and the procedure in the runbook.
**Alternatives considered**: (a) Self-managed Postgres with hand-rolled backups - rejected: no SRE function, and backup tooling nobody exercises is the classic silent failure. (b) Hot standby with automatic failover - rejected for v1 on cost and complexity against the per-team ceiling, recorded rather than assumed away; it is the first thing to add if the RTO proves unacceptable. (c) Nightly logical dumps only - rejected: an RPO of up to 24 hours would lose the acknowledgment and escalation history that is the product's evidentiary value.
**Consequences**: Easier - a concrete, testable recovery story for the SPOF; the rehearsal converts an assumption into evidence. Harder - a one-hour RTO is a one-hour total outage for writes and the authenticated view, which no cache mitigates; up to five minutes of notification and acknowledgment history can be lost, so the Delivery Log could be missing records for the very window an incident review cares about; rehearsals cost engineer time quarterly on a 2-3 person team, and skipping them silently reverts this ADR to a hope.

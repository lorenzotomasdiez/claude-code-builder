# Research log

Append-only history of the `/gnhf-research-run` loop.

Each entry is written by the GNHF worker at the end of its own run, before it opens the PR.
The next run reads this file first so it does not re-investigate the same ground.

Do not edit past entries. If a decision from a past entry turns out to be wrong, say so in a new entry instead of rewriting history.

## Format

```
## YYYY-MM-DD - <one-line topic>

- Investigated: <what was researched, and where - community sources, competing tools, repo gaps>
- Decision: <what was built or changed, and why this over the alternatives considered>
- Result: <workflow/file touched, PR link, smoke-test outcome>
- Next: <a concrete follow-up or open question for a future run, if any>
```

DEV Community's "How AI Coding Agents Will Choose Your SaaS Boilerplate in 2026" - "scaffold me a SaaS app with auth, billing, and a dashboard" is now a baseline prompt agents are expected to handle well, meaning the shared-schema/JWT-tenant-claim/background-job architectures this workflow reviews are already being built fast by agents. Repo gap: `security-audit`'s five lenses (injection/authn/authz/secrets/supply-chain/AI-LLM) come close but none is scoped to cross-tenant data leakage specifically; no expert file or workflow in the repo covers it.

Considered and set aside: a `billing-integration-reviewer` (real but narrower, one vendor integration rather than a recurring architectural property) and an AGENTS.md generator (real trend, wrong shape for this repo's workflow-library format). - Result: `tenant-isolation-audit/` (full anatomy: 7 agents, 1 workflow script, 1 command, 1 README). PR: https://github.com/lorenzotomasdiez/claude-code-builder/pull/1 (open against `main`, not merged). Smoke test: PASS - real end-to-end run via headless `claude -p` against a fixture app with two planted bugs (an unscoped order-lookup route, an unscoped nightly export job); both caught and confirmed by independent verifiers, the export-job bug independently caught by three lenses from three angles and correctly deduplicated into one report entry, zero false positives on the correctly-scoped control route and on the `authz` lens. Full detail in `tenant-isolation-audit/README.md`.
- Next: `security-audit` and `tenant-isolation-audit` currently overlap only at the AI/LLM surface by design (one asks "is this prompt injectable," the other asks "does this prompt/retrieval/tool-call carry another tenant's data") - a future run could consider whether they should share a combined entry point once both have more real-world usage, though splitting them was the right call for now since tenant leakage needed lenses (data-layer, background-jobs) security-audit has no equivalent of. ## 2026-07-28 - Reasoning-effort selection (opts.effort), a second unused lever like model tiering

- Investigated: This run is scoped to the meta level per its prompt - how the workflows themselves are engineered, not a new domain workflow - so first read `CLAUDE.md`, `RESEARCH_LOG.md` (above entry), and `gh pr list --state all` (one prior PR, merged, for `tenant-isolation-audit`, out of scope for this run by the prompt's own instruction). Read `MODEL_SELECTION.md`, `STATUS.md`, and the `context-bloat-forensics` repo-internal tool in full, plus `prd-generator.js` and `code-review.js` as anatomy references. Web research (WebSearch, primary/current sources): the Claude Agent SDK's `agent()`/subagent call surface exposes a per-call `effort` field (`low`/`medium`/`high`/`xhigh`/`max`) that sets the extended-thinking/reasoning budget independently of model choice - confirmed via `platform.claude.com/docs/en/agent-sdk/subagents`, current community writeups on 2026 Claude Agent SDK subagent configuration, and open `anthropics/claude-code` feature-request issues discussing per-subagent effort control, all converging on the same point community-side: mechanical subagent tasks (extraction, formatting, enumeration) don't benefit from a deep reasoning budget but pay its latency/cost by default under an inherited session effort, while judgment-heavy tasks (adversarial verification, synthesis) benefit from a wider one. Repo gap: grepped all 32 `.claude/workflows/*.js` scripts for `effort:` - the only hit was an unrelated schema field literally named `effort` in `feedback-triage` (US t-shirt sizing for a feedback theme, nothing to do with reasoning budget). Every one of the 33 Opus-pinned judgment phases documented in `MODEL_SELECTION.md`, and every mechanical scope/discover phase in every workflow, was running on the session's inherited default effort - the exact same missed distinction `MODEL_SELECTION.md` already fixed for `model`, one lever over, never addressed for `effort`.
- Decision: Wrote `EFFORT_SELECTION.md` (sibling to `MODEL_SELECTION.md`, same shape: why this exists, the rule per phase kind, a retrofit table, smoke-test evidence, how to change it later) establishing the rule: mechanical/extraction phases get `effort: 'low'`, breadth/fan-out phases stay on the session default (unmarked, correct as-is), and judgment phases that already carry `model: 'opus'` also get `effort: 'high'` or `'xhigh'` since the two levers should move together for the same reason. Retrofitted it into three real scripts to prove it, not just propose it: the repo-internal `context-bloat-forensics` tool (Discover: `low`, Synthesize: `high`) and the two flagship adversarial-review workflows `code-review` and `security-audit` (Scope: `low`, Verify: `xhigh` alongside their existing `model: 'opus'`), chosen because they share one shape (scope -> parallel lenses -> adversarial verify -> report) so the same fix proves it generalizes across a family, not one script. Considered and set aside: retrofitting all 32 scripts in one pass - correct in principle but the objective calls for one demonstrated, verified improvement, not a repo-wide edit no single run can fully re-verify; left as the explicit next step in `EFFORT_SELECTION.md` and `BACKLOG.md`.
- Result: `EFFORT_SELECTION.md` (new), `code-review/.claude/workflows/code-review.js`, `security-audit/.claude/workflows/security-audit.js`, `.claude/workflows/context-bloat-forensics.js` (all edited), `reports/context-bloat-forensics/README.md` (smoke-test record appended), `BACKLOG.md` (builder note added). `node scripts/validate-workflow.mjs --all` still passes for both retrofitted packages after the edit. Smoke test: PASS - `context-bloat-forensics` invoked live via the Workflow tool against a trivial one-line fixture folder (`/tmp/cbf-smoke-test/journal.jsonl`) after adding the new `effort` values; all 4 agents completed, Discover -> Narrate -> Critique -> Synthesize ran in the right order, every schema validated, no errors. `code-review` and `security-audit` were not re-run end to end for this change (both already carry their own recorded smoke-test PASS from before this retrofit, and adding `opts.effort` to an existing call changes no control flow or schema) - re-spending a full adversarial fan-out on both a second time to re-prove a mechanism the live `context-bloat-forensics` run already proved would violate this repo's own "never run an expensive fan-out more than once" rule.
- Next: apply `effort: 'low'` to every scoping/discovery/mapping phase and `effort: 'high'`/`'xhigh'` to every phase already carrying `model: 'opus'` across the remaining 29 workflow scripts, the same way `MODEL_SELECTION.md`'s tiering was retrofitted workflow by workflow over time. A `STATUS.md`-style single-line-per-workflow effort table (mirroring the `MODEL_SELECTION.md` table) would make the remaining gap as visible as the "Solid/Needs review/Never verified" table already makes smoke-test status.

## 2026-07-28 - Schema field descriptions on enum properties, a gap in every workflow's structured output

- Investigated: Scoped to the meta level per this run's prompt - not a new domain workflow. Read `CLAUDE.md`, both prior `RESEARCH_LOG.md` entries above (tenant-isolation-audit is a domain workflow, out of scope; effort tiering already merged, its own "Next" item was left as an open retrofit but is a continuation of an already-covered improvement, not a new one), and `gh pr list --state all` (2 PRs, both merged). Read `prd-generator.js`, `code-review.js`, `security-audit.js` as anatomy references and `scripts/validate-workflow.mjs` in full to understand what the repo's own quality gate already checks. Web research (WebSearch, primary/current sources): Anthropic's Agent SDK structured-outputs docs (`platform.claude.com/docs/en/agent-sdk/structured-outputs`, and the equivalent `code.claude.com` page) state the schema-design best practice directly - "use enum when valid options are known, and string fields with descriptions when content is variable" - and warn that "structured outputs constrain format, not quality: a poorly prompted agent with a perfect schema will give you valid JSON containing wrong answers." Repo gap: grepped every `.claude/workflows/*.js` for `enum:` - 109 hits across 30 packages, zero of them with an adjacent `description:` field. The two highest-stakes examples are `severity` (drives what a human sees as urgent) and `verdict: confirmed/rejected` (drives what an adversarial-verification loop discards as a false positive) - both present in `code-review` and `security-audit`, both left for the subagent to infer the boundary between adjacent values with no anchor in the schema itself.
- Decision: Wrote `SCHEMA_DESIGN.md` (sibling to `MODEL_SELECTION.md` and `EFFORT_SELECTION.md`, same shape) establishing the rule: every schema field with an `enum` gets a `description` stating the calibration between its listed values, not just what the values are. Retrofitted it into three real scripts to prove it: `code-review` and `security-audit` (`severity` and `verdict` in both, chosen for the same reason `EFFORT_SELECTION.md` chose them - identical scope/lens/verify/report shape, so the fix proves it generalizes across a family) and the repo-internal `context-bloat-forensics` tool (`kind`, `readMode`, event `type`, `severity` - four enum fields, the most in one script, and the one workflow this repo can smoke-test end to end cheaply). Considered and rejected: adding a mechanical check to `scripts/validate-workflow.mjs` that flags enum fields without a description. Attempted this first (a regex-based check mirroring the existing schema-reference check, designed as a non-blocking WARN like the existing "never smoke-tested" check, specifically to avoid turning 28 currently-passing packages red in one PR) but the `Edit` tool refused: `.claude/settings.json` denies `Edit` on `scripts/**` (also `experts/**` and `prd-generator/.claude/**`) as a deliberate guard rail so no agent, including this one, can weaken or extend its own quality gate. Respected that boundary rather than working around it with Bash or Write; `SCHEMA_DESIGN.md` records this as the reason enforcement is a documented convention for now, same as `MODEL_SELECTION.md` and `EFFORT_SELECTION.md`, and names it as a human-only next step.
- Result: `SCHEMA_DESIGN.md` (new), `code-review/.claude/workflows/code-review.js`, `security-audit/.claude/workflows/security-audit.js`, `.claude/workflows/context-bloat-forensics.js` (all edited to add `description` to their enum fields), `code-review/README.md`, `security-audit/README.md`, `reports/context-bloat-forensics/README.md` (smoke-test addenda appended), `BACKLOG.md` (builder note added). `node scripts/validate-workflow.mjs --all` still passes clean (no new failures) for every package, including the three retrofitted ones. Smoke test: PASS - `context-bloat-forensics` invoked live via the Workflow tool against a fresh trivial fixture folder (`/tmp/cbf-smoke-test-2/journal.jsonl`) after adding `description` to all four of its enum fields; all 4 agents completed, Discover -> Narrate -> Critique -> Synthesize ran in order, every schema (now carrying the new `description` fields) validated on the first attempt with no SDK rejection or retry, and the enum values chosen (`kind: "workflow-journal"`, `readMode: "full"`, event types `"command_invoked"`/`"unclear"`) matched the new descriptions' calibration criteria. `code-review` and `security-audit` were not re-run end to end for this change - both already carry their own recorded full-fan-out smoke-test PASS from before this retrofit, adding a `description` string changes no required field, enum value, or control flow, and the live `context-bloat-forensics` run already proves the SDK accepts `description` on an `enum` field without incident; re-spending a full adversarial fan-out on both a second time to re-prove that mechanism would violate this repo's own "never run an expensive fan-out more than once" rule.
- Next: apply `description` to the enum fields in the remaining 28 workflow packages that use `enum` schema fields but do not yet have it, the same incremental way `MODEL_SELECTION.md` and `EFFORT_SELECTION.md` are being retrofitted. Separately, a human maintainer (not an agent, since `scripts/**` is edit-denied) could decide to promote this from a documented convention into an actual `validate-workflow.mjs` check - as a non-blocking WARN first, given the current 28-package gap, the same way the existing "never smoke-tested" state is a WARN and not a hard FAIL.

## Narrative

This folder captures a single end-to-end run (`wf_21082588-a5e`) of the **tech-stack-selector** workflow, invoked at 2026-07-28T00:48:46Z against a PRD for "Chiri," a browser-only AI-assisted Markdown editor, with the constraint that shadcn/ui was pre-decided.

The run followed the workflow's designed pipeline: **Frame -> Research -> Score -> Author -> Critique/Revise (capped loop)**.

1. **Frame** - one `stack-framer` agent (opus) read the PRD and derived 5 decision areas (pending-suggestion representation, AI edit request/response contract, word-level diff computation, client-side session state, app scaffold/tooling), each with weighted criteria and hard constraints.
2. **Research** - 5 `stack-researcher` agents (sonnet) ran in parallel/pipeline, one per decision area, each firing several WebSearch/WebFetch calls (ProseMirror vs marks, XState/Zustand/Redux, Vite vs Next.js static export vs CDN-only, jsdiff/prosemirror-changeset/diff-match-patch, OpenRouter streaming/CORS) and returning sourced candidate evidence via StructuredOutput. One WebFetch (npm 403) failed but did not block the agent.
3. **Score** - 5 `stack-scorer` agents (opus) each received the full researcher evidence blob pasted inline into their prompt and returned a weighted scoring matrix, winner, and runner-up per area (XState, Vite+React+TS, custom ProseMirror marks, prosemirror-changeset, raw streaming text delta).
4. **Author** - a `stack-author` agent (sonnet) received the entire framing object plus all 5 scoring matrices inline (92,802 tokens in one turn) and wrote the first tech-stack decision document (v0.1, 21,487 chars) to `docs/product-specs/chiri-requirement-md-tech-stack.md`, linking it into the PRD.
5. **Critique round 1** - 3 `stack-critic` agents (opus), one per lens (integration-coherence, evidence-quality, boring-alternative), each independently read the full document and all returned `needs_revision` (10, 14, 18 issues).
6. **Revise round 1** - the `stack-author` agent re-read the doc, addressed critique, and overwrote it as v0.2 (32,500 chars reported, though the actual Write payload was ~71,448 chars - a mismatched self-report). This was the single most expensive step of the run (67,079 tokens, ~414s).
7. **Critique round 2** - the same 3 lenses re-ran against v0.2 and again all returned `needs_revision` (8, 6, 18 issues), with evidence-quality repeating the same issue count as round 1.
8. Round cap (2) was reached; the workflow stopped, returned the best draft (v0.2), and truncated the reported open-issues list from 32 to 15 with a pointer to the document's critique history.

The run completed successfully (status "completed," 19 agent invocations, 479,091 total tokens, 81 tool calls, ~19.3 minutes), but ended with all three review lenses still unsatisfied and no third round to resolve them.

## Recommendations for the workflow library

**`tech-stack-selector` workflow / `.claude/workflows/tech-stack-selector.js`:**
- Add an intermediate-artifact convention: have `stack-researcher` and `stack-scorer` phases write their JSON output to per-area scratch files (e.g. under `docs/product-specs/_work/<area-slug>.json`) instead of returning it purely in-memory, and have subsequent phases (`stack-scorer`, `stack-author`) reference those files by path rather than receiving `JSON.stringify()`'d payloads inline in prompts. This directly targets findings #1 and #2, which together account for the single largest token/time costs in the run (Author phase at 92,802 tokens, Revise phase at 67,079 tokens/414s).
- Change the critique-to-revise handoff to require lens issues to cite section/line references rather than quoting document text, and change the revise step to apply targeted edits to only flagged sections instead of a full read-then-overwrite. This addresses finding #3 and would likely have prevented the document's 51% size growth between v0.1 and v0.2 without resolving the underlying issues.
- Split the authored tech-stack decision document by section (or otherwise keep it under ~20k tokens) so a single `Read` call suffices; this removes the truncation/retry tax paid independently by all 3 parallel `stack-critic` agents in both rounds (finding #4, recurrence 3, and finding #7).
- Add a post-write validation step that computes `charCount` (and any other size/version metadata) from the actual file on disk rather than trusting the agent's self-reported StructuredOutput field, and reject/retry on mismatch (finding #6).
- Reconsider the review-loop's exit behavior: when `MAX_ROUNDS` (currently 2) is reached with lenses still returning `needs_revision`, escalate the specific unresolved issues explicitly in the workflow's final output/README rather than silently returning "best draft" with a truncated issue list (finding #5). Consider whether a 3rd round or a different revise strategy (targeted diffs, per finding #3) would let evidence-quality actually converge, since it made zero measurable progress across the two rounds observed here (18 issues both times).

**Open questions (not findings, worth checking separately):**
- Whether this same duplication-into-prompt pattern (rather than file-reference) exists in other workflows built from the same `prd-generator` template, particularly any workflow with a research→score→author→critique shape.
- Whether the `MAX_OPEN_ISSUES=15` truncation-with-pointer behavior in the final result is documented anywhere the workflow's consumer would see it, since 17 of 32 real issues are silently dropped from the direct output.

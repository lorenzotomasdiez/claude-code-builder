## Narrative

The audited folder (`/Users/lorenzotomasdiez/projects/workflows-folder-test`) contains two very different kinds of material: (1) the static library itself - subagent definitions under `.claude/agents/*.md` and command entry points under `.claude/commands/*.md` for seven workflows (`prd-generator-v2`, `architecture-designer`, `tech-stack-selector`, `design-system-foundation-v2`, `task-breakdown`, `tdd-blueprint`, `feature-implementer`) - and (2) the actual output artifacts produced by running those workflows once, end-to-end, against a real product idea: a "Chiri Markdown Editor." The overwhelming majority of individual files audited (roughly 50 of ~65) are static agent/command definitions with no execution trace in them at all; they describe intended behavior (tool restrictions, output schemas, "what you do not do" sections) but contain no evidence of ever being invoked. The real story of what happened is reconstructable only from the dated, versioned output documents under `docs/`.

Chronologically: `/prd-generator-v2` produced `docs/product-specs/chiri-requirement-md-prd.md`, reaching v0.5 by 2026-07-28, with an open requirement (R-08) revised after discovering its default model had no live serving provider on OpenRouter. `/tech-stack-selector` then produced `chiri-requirement-md-tech-stack.md`, iterating v0.2 -> v0.4 across 2026-07-27 to 2026-07-29, incorporating real spike evidence (a hands-on test of `prosemirror-suggestion-mode@1.0.79`, a live OpenRouter pricing/availability check, a Tiptap-integration spike, and a live `gpt-4o-mini` structured-output/latency test) that flipped its primary recommendation twice.

`/architecture-designer` then ran and produced by far the most turbulent artifact in the set: a single architecture document that went through fourteen revisions (v0.1-v0.14) between 2026-07-27 and 2026-07-29. It absorbed a large batch of new ADRs and decisions in v0.5-v0.6, ran three trim passes (v0.2-v0.4) and two more (v0.7-v0.8) against a self-imposed ~30,000-character ceiling without ever meeting it, discovered in v0.10 that it had wrongly assumed the tech-stack document didn't exist and had duplicated/invented decisions the tech-stack document already owned, flip-flopped ADR-003/ADR-005 in v0.11 after new spike evidence, ran a dedicated sixth trim pass that still left it at ~188,000 characters against the 30,000-character target, withdrew the ceiling in v0.13, and only in v0.14 split the single ~161,000-character document into five separate files (main doc, ADRs, tech-stack records, risks-and-questions, decision log).

`/design-system-foundation-v2` produced a clean, non-turbulent set of design-system docs (ux-principles, components, implementation-contract, component-map, gallery-plan, design-tokens, usage-rules), each landing at a modest version (v0.2-v0.4) with no comparable thrashing. `/task-breakdown` then produced `tasks.md` (v0.2), decomposing the work into fourteen tasks (T0-T13) each cross-referencing the PRD/architecture/tech-stack/design-system docs. Finally `/tdd-blueprint` ran three times, once per task (T0, T1, T2), each time producing a `specs.json` work file plus `tdd-plan.md`, `test-strategy.md`, `traceability-matrix.md`, `test-data-and-fixtures.md`, `behavior-specs.md`, and (for T1/T2) an `nfr-test-plan.md`. These runs show internal self-correction (duplicate specs removed, orphaned specs pruned) but also leave a number of documented, unresolved contradictions between sibling spec documents (conflicting env-var allow-lists, conflicting focusable-element counts, conflicting HMR probe file paths) explicitly deferred to a human implementer. A final `test-results/.last-run.json` shows the resulting test suite passing with no failures.

| 2 | Oversized/undecomposed monolithic document (reported both as "oversized input" and "missing decomposition") | High | 2 (same root cause, reported independently from the two architecture files) | `chiri-requirement-md-architecture.md` (single document ~161,000-188,000 characters across v0.2-v0.13); `chiri-requirement-md-architecture-decision-log.md` line 58 (only split into 5 files at v0.14, "reversal of the v0.13 decision to keep one file") | Split by reading-occasion (ADRs / tech-stack records / risks-and-questions / decision log / entry point) as soon as the categories stabilize (around v0.6-v0.11 here), not after 6 failed trim passes and 13 full-document revisions each requiring the whole oversized file to be reloaded into context. |

## Recommendations for the workflow library

**`architecture-designer` workflow / `architecture-writer` and `architecture-critic` agents** (`.claude/workflows/architecture-designer.js`, `.claude/agents/architecture-writer.md`, `.claude/agents/architecture-critic.md`)
- Add a hard cap on trim-pass rounds (findings #1, #2). The transcript shows six trim passes against a ~30,000-character ceiling that was never met and eventually withdrawn - that entire cycle should have been cut off after 1-2 failed attempts with an automatic escalation to "split the document" rather than "trim again."
- Move the file-split decision earlier in the pipeline. `architecture-writer` should decompose into per-section files (ADRs, tech-stack records, risks-and-questions, decision log, entry point) as soon as the ADR set stabilizes, not after the document has already ballooned past 150,000 characters through 13 full-document revisions.
- Before `architecture-writer` derives a decision in an area (e.g. suggestion-layer choice, model output format), have it explicitly check whether a linked companion document (e.g. the tech-stack document from `tech-stack-selector`) already owns that decision area, and reference it rather than re-deriving it (finding #3). The v0.10 reversal in the decision log shows this check was missing and caused rework of two load-bearing ADRs.

**`tdd-blueprint` workflow / spec-authoring agents** (`.claude/workflows/tdd-blueprint.js`, `.claude/agents/tdd-spec-author.md`, `.claude/agents/tdd-nfr-spec-author.md`, `.claude/agents/tdd-scratch-writer.md`)
- Have the workflow write per-group spec files (or an index file plus per-group detail files) instead of a single flat `specs.json` bundling functional and all four NFR groups together (finding #4), so a downstream consumer needing only, say, resilience specs can read a fifth of the content.
- Add a small metadata header (producing workflow/agent, timestamp, source docs) to generated `_work/*.json` artifacts to make later provenance/context audits possible without needing the raw transcript (finding #6).

**Open question, not a finding** - several output-only files (T0 `specs.json`, T1 `traceability-matrix.md`) contain no trace of the tool calls/agent turns that produced or consumed them, so it could not be determined whether those specific `tdd-blueprint` runs exhibited context bloat (e.g. whether the full spec set was pasted inline into multiple parallel critic/lens agents versus referenced by path). Worth checking directly against the workflow's actual execution transcript, if retained, since `tdd-critic.md` and `tdd-sequencer.md` definitions suggest multiple agents are meant to read these files independently by path rather than receiving their content inline - confirming that pattern held in practice would validate or rule out a duplication-instead-of-reference risk in `tdd-blueprint.js`.

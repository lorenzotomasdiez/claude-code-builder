# Workflow backlog

Build these in order. Each is a self-contained workflow following the anatomy and quality bar in `CLAUDE.md`, with `archive/prd-generator/` as the reference.
Build one complete workflow per iteration. Distill the relevant `experts/*.md` into each workflow's own subagents.

This file lists every workflow ever built here in build order, regardless of where it physically lives today. Root `README.md` names the 16 current flagships; everything else here now lives under `archive/` (see `archive/README.md` for why) but keeps its full entry below for history.

These are the recurring tasks a product and engineering team actually does day to day, ordered by how often the workflow would get reused (most-used first), so if a run only finishes the first few, they are the highest-value ones.
You may add workflows beyond this list when you judge them valuable; if you do, append them here with a one-line intent and mark them `[added]`.

## Daily engineering (highest reuse, build first)

1. `code-review` - multi-lens adversarial review of a diff or PR: correctness, security, performance, tests, readability as independent parallel lenses; adversarially verify each finding to kill false positives; output findings ranked by severity. This is the flagship pattern. Experts: software-developer, qa-architect, software-architect, pentester.
2. `feature-implementer` - take a ticket or user story to a PR: clarify the requirement, plan with an architect lens, implement in small slices, write tests, self-review, and draft the PR body. Experts: software-developer, software-architect, qa-engineer.
3. `bug-hunter` - reproduce the bug end-to-end first (as a user would hit it), fan out parallel root-cause hypotheses, converge on the real cause, fix it, add a regression test, and verify. Experts: software-developer, qa-engineer.
4. `test-backfill` - find the highest-risk under-tested code, generate meaningful tests (not coverage theater), and prove each test actually catches a real regression. Experts: qa-engineer, qa-architect, software-developer.
5. `dependency-upgrade` - assess an upgrade: breaking changes, migration steps, security advisories; apply it; verify the build and tests still pass. Experts: software-developer, devops-engineer, pentester.
6. `security-audit` - authorized OWASP plus AI/LLM security review over a diff or service: parallel attack-surface lenses, adversarially verify each finding, output a ranked report. Assumes explicit authorization. Experts: pentester, qa-architect, software-architect.
7. `perf-investigation` - hypothesize performance hotspots, gather evidence, rank issues by impact, and propose fixes with an expected gain for each. Experts: software-architect, software-developer, devops-engineer.

## Product and delivery (recurring, cross-functional)

8. `technical-solution-proposal` - take a PRD and produce a proposed technical solution for how the app gets built, by having the experts interact rather than review in isolation: each expert (architect, backend/dev, frontend, devops, QA, security) puts forward an approach, they cross-examine each other's proposals over a few debate rounds, disagreements are surfaced explicitly, and a synthesis agent resolves them into one coherent proposal with the trade-offs and open questions recorded. This is the panel-debate pattern, distinct from independent parallel lenses. Experts: software-architect, software-developer, python-developer, astro-developer, devops-engineer, qa-architect, pentester.
9. `spike-research` - answer a "should we adopt X" or "how is Y usually solved" question: multi-modal sourced research, an options matrix, and a recommendation with a stated confidence level. Experts: researcher, software-architect, product-owner.
10. `epic-breakdown` - turn a PRD or raw idea into stories with acceptance criteria, estimates, sequencing, and risks. Experts: product-owner, project-manager, software-architect.
11. `status-report` - synthesize git activity and changed files (plus optional ticket input) into a stakeholder-readable status or standup update, tuned per audience. Experts: project-manager, product-owner.
12. `release-readiness` - go/no-go check across tests, security, docs, migrations, and rollback plan; each an independent gate; blocking if any gate fails. Experts: qa-architect, devops-engineer, project-manager.
13. `docs-sync` - detect drift between code and its docs, README, and ADRs, then propose targeted updates. Experts: software-developer, researcher, software-architect.

## Greenfield and product (occasional, lower daily reuse)

14. `architecture-designer` - produce the architecture document set the "Fundamentals of Software Architecture" way for a new service or feature: architecture characteristics, component design, ADRs, tech-stack decision records. Experts: software-architect.
15. `feedback-triage` - cluster raw user feedback into product signals, opportunities, and prioritized bets. Experts: product-owner, researcher, marketing-expert.
16. `qa-suite` [added] - QA a service/area end to end: the qa-architect inventories existing tests and docs and designs a layered test strategy (unit/integration/e2e/contract/performance) with concrete gaps, the qa-engineer writes the missing tests and runs the suite, a coverage critic verifies the delivered tests cover the strategy (capped loop), and a reporter writes up findings and remaining risk. Experts: qa-architect, qa-engineer.
17. `qa-suite-pro` [added] - everything qa-suite does PLUS a real browser E2E pass: the architect also derives UI user stories, a story-author persists them as Bowser-format YAML in a timestamped run folder, and one browser-runner per story drives playwright-cli step-by-step with screenshots and pass/fail, all synthesized into one report. Headless by default, or headed (a real, visible window per story) via a `headed` toggle - same engine, same parallelism, just an extra flag. Assumes playwright-cli installed. Browser how-to ported from the builder repo's Bowser system (`bowser-qa-agent`, which itself uses playwright-cli --headed, not computer-use) and embedded in the browser-runner agent. Mechanical steps (scoper, story-author, browser-runner) run on haiku; judgment/synthesis steps (architect, engineer, coverage-critic, reporter) stay on sonnet. Experts: qa-architect, qa-engineer. A separate `qa-suite-pro-computer-use` workflow was built and then folded back into this one after a real run showed Claude's computer-use / in-Chrome tools need an interactive session with the Chrome extension connected, which subagents in a background Workflow run never have - every run came back all-blocked.
18. `design-blueprint` [added] - turn a product idea or PRD into a set of buildable UX/UI design documents via a cross-examining panel debate (UX designer, product owner, growth) that weighs what works best for the user against what is most profitable and what is worth building first; a synthesizer resolves the tensions into structured decisions and four document authors write design-decisions, user-flows, screens-and-ui, and landing-page in parallel. Panel-debate pattern (like technical-solution-proposal) pointed at product/UX/business. Experts: ux-designer (new), product-owner, marketing-expert.

19. `client-requirement-shaping` [added] - the step BEFORE `prd-generator`: turn a vague client ask into a buildable proposal. Intake separates what the client asked for from what they actually need, four research lenses gather sourced findings with graded confidence, eight expert seats (systems architect, pragmatic architect, UX designer, user researcher, product owner, business model, delivery lead, domain skeptic) propose independently and then cross-examine each other over capped rounds, and two outside voices who were never in the debate judge the result: a reductionist who returns the minimal version and a `proportionate`/`overbuilt` verdict, and a devil's advocate who builds the honest case against building it at all with kill criteria. Either outside voice can send the panel back for an answer round. A synthesizer decides rather than averages and records unresolved disagreements, then two authors write a client proposal and a PRD-ready seed in parallel. Produces no code. Output feeds `/prd-generator`. Experts: software-architect, ux-designer, user-researcher (new), product-owner, business-strategist (new), scope-reductionist (new), project-manager, researcher.

20. `tdd-blueprint` [added] - the step BETWEEN the design workflows and the developer: turn a PRD plus whatever `architecture-designer` and `design-blueprint` produced into the test blueprint a developer does TDD from, writing no code at all. A framer turns the upstream docs into a testable-surface brief (behavior slices sized to about a day of red-green work, components, external dependencies, NFR targets, honest ambiguities), a strategist decides the suite shape, layer boundaries, and the test-double policy dependency by dependency, then one spec author per slice plus one per cross-cutting concern (performance, security, accessibility, resilience/data) write Given/When/Then specs with stable IDs, concrete data, and a layer each. Three adversarial lenses review the WHOLE spec set (coverage-completeness, testability-determinism, tdd-usability - "could a developer write this before the code exists"), issues are routed back to the group that owns the fix with a coverage-gap sweep for the unowned ones, capped at 2 rounds. A sequencer then decides the red-green build order (naming the first failing spec of every step) and the traceability matrix, and six authors write the documents in parallel. Output feeds `/feature-implementer` starting red. Experts: qa-architect, qa-engineer.

21. `tech-stack-selector` [added] - the step BETWEEN `prd-generator` and `architecture-designer`: turn a PRD into a researched, weighted tech-stack decision matrix instead of letting the architecture document invent its stack table from memory (its writer is explicitly told not to research). A framer derives the decision areas that are genuinely open for this product (max 5, ranked by stakes) and the weighted criteria for each, traced back to PRD drivers, naming no technology; then per area a researcher gathers sourced candidate evidence (versions with as-of dates, license, cost at the stated scale, operational burden, known failure modes, lock-in) including the boring/default option on equal footing, and a separate scorer grades it 1-5 per weighted criterion so the agent that finds the evidence is not the agent that grades it. Research and scoring are pipelined per area; a barrier before critique because coherence is a cross-area property. Three adversarial lenses (integration-coherence, evidence-quality, boring-alternative) review the whole document, capped at 2 rounds. Output feeds `/architecture-designer` by pasting it into the request; `architecture-designer` is left unmodified. Experts: software-architect, researcher, devops-engineer.

22. `gnhf-backlog-maker` [added] - turn a raw task ("update all the design docs, write the tests and implementations, and verify everything works") into an exhaustive, verification-bearing `backlog.md` and a ready-to-launch GNHF worker prompt, so an autonomous GNHF loop can grind through the work unattended without anything missing. A scoper detects the repo's real gate-chain commands and any existing backlog to continue; a decomposer (opus - completeness is the judgment call) breaks the task into already-sequenced vertical-slice rows, each bundling a concrete deliverable, its real test, and its real verification; a writer assembles/merges them into backlog.md without ever overwriting existing rows; three adversarial critics (completeness, verification-rigor, sequencing/scope) review before the GNHF launch prompt is composed deterministically from the gate-chain commands and non-goals. Experts: qa-architect, software-architect, project-manager.
23. `design-system-foundation` [added] - the step BETWEEN `design-blueprint` and the developer: turn the design documents into a stack-agnostic design system so UI work starts from decisions already made instead of the implementer inventing spacing, states, and error treatments on the spot. A framer inventories only the UI surface the source documents actually describe, tracing every screen, element, and component need back to where it came from; principles and tokens are then derived in parallel (tokens with computed WCAG contrast ratios, not asserted ones, and a mechanical mapping to CSS vars / Tailwind / `tokens.json` / native constants / Figma variables); up to 4 component-group authors write implementation-independent contracts with a mandatory non-empty `tracedTo`, every state, and full accessibility, rejecting anything unearned; a rules author then sees the whole catalog and settles the recurring "which one do I reach for" decisions (modal vs page, toast vs inline, skeleton vs spinner, undo vs confirm) each with a required default and an explicit never - the layer most design systems skip and the reason catalogs still produce inconsistent products. Five documents are authored in parallel, then four adversarial lenses review the WHOLE set (justification - deletes any component, token, or rule no surface earns, and is the most important seat; accessibility - recomputes marginal contrast rather than trusting the table; consistency; implementability - fails the set if a framework name leaks in), with issues routed back to the one document that owns each fix so a round re-authors only the flagged documents. Capped at 2 rounds. There is deliberately no separate accessibility document: contrast lives in the token tables, keyboard and focus in the component contracts, and the checks in the implementation contract's verification table. Stack agnostic but not platform agnostic - it takes a platform target, because component contracts genuinely do not port across web/iOS/Android. Output feeds `/tdd-blueprint`, `/feature-implementer`, and `/code-review`. Experts: design-systems-engineer (new), ux-designer.

24. `shadcn-installer` [added] - install shadcn/ui into whatever project it is run in, tech-stack agnostic. A detector classifies the framework (Next.js, Vite, Remix, Astro, Laravel, Gatsby, React Router, TanStack Router/Start, or manual), package manager, TypeScript usage, Tailwind version, and any existing shadcn state before anything runs; an init engineer fetches the live per-framework install doc rather than trusting memorized CLI flags and runs or manually performs the init (skipped if `components.json` already exists, for idempotency); a component engineer installs the requested (or a default starter) component set; a verifier independently re-checks `components.json`, CSS theme wiring, and component imports and best-effort runs the project's own build, routing any issue back to whichever engineer owns it for a capped fix loop; a reporter writes the install record. Unlike the rest of this library it is not a document generator - its job is to actually mutate the target project's files. Experts: none distilled (embeds the shadcn CLI/doc how-to directly, matching how `qa-suite-pro` embeds playwright-cli rather than adding an expert file for a single tool's command surface).

25. `tenant-isolation-audit` [added] - a `security-audit`-shaped audit for the one failure class that is specific to running a SaaS product rather than any single application: tenant-boundary leaks. Added after research (July 2026) found this is the recurring architectural gap in AI-era multi-tenant SaaS - a leaked row does not just return the wrong response, it can enter an agent's reasoning chain and be acted on through a further tool call - and that no existing workflow or expert file in this repo covers it, even though `security-audit`'s five lenses (injection/authn/secrets/supply-chain/AI-LLM) come close. A scoper maps the tenancy model, tenant-context carriers, and boundary-crossing entry points; four independent lenses (data-layer, authz/session, background-jobs, integrations/AI-context) audit in parallel; every finding is adversarially verified by an agent with no stake in being right, blind to which lens raised it; a reporter ranks, deduplicates, and adds remediation guidance to what survives. Experts: software-architect, pentester, devops-engineer.

## Notes for the builder

- Each workflow must be independently runnable with a trivial or mock input for its smoke test, even when it would normally consume another workflow's output. Document any such dependency in the README.
- Favor the orchestration patterns that fit the task: parallel lenses for review and research, adversarial verify to kill false findings, loop-until-clean for revise cycles, pipeline for per-item independent stages. Do not force a linear chain where a fan-out is more honest.
- If a role you need is not in `experts/`, add the file there first, then build the workflow.
- Prefer finishing and smoke-testing one workflow over starting the next.
- `EFFORT_SELECTION.md` documents a per-phase `opts.effort` rule (mirroring `MODEL_SELECTION.md`'s per-phase `opts.model` rule), retrofitted so far into `context-bloat-forensics`, `code-review`, and `security-audit`. A future run should apply it to the remaining workflow scripts: `effort: 'low'` on scoping/discovery phases, `effort: 'high'`/`'xhigh'` on phases already pinned to `model: 'opus'`.
- `SCHEMA_DESIGN.md` documents a rule for JSON schema `enum` fields: every `enum` gets a `description` stating the calibration between its values, not just the values themselves. Retrofitted so far into `context-bloat-forensics`, `code-review`, and `security-audit`. 28 of 30 workflow packages that use `enum` schema fields still need this; `scripts/validate-workflow.mjs` is edit-denied to agents (see `.claude/settings.json`), so a human maintainer needs to decide whether to promote this from a documented convention into an enforced check there.
- `UNTRUSTED_INPUT_HANDLING.md` documents a rule for any agent whose `tools:` frontmatter includes `WebFetch`/`WebSearch`: add a "Handling fetched content" section instructing it to treat fetched pages/search results as data, not instructions, and to report (not obey) any embedded directive. Retrofitted so far into `dependency-upgrade-security-advisor`, `spike-research-community-lens`, and `stack-researcher` (`tech-stack-selector`). 10 of 13 WebFetch/WebSearch-capable agents in the repo still need this: `client-requirement-shaping/crs-researcher`, both `competitor-design-tokens` agents, both `prd-generator`/`prd-generator-v2` researchers, `shadcn-installer/shadcn-init-engineer`, and the three remaining `spike-research` lenses plus its verifier.
- `PROMPT_CACHE_ORDERING.md` documents a rule for any prompt-building function called repeatedly (in a `parallel()` fan-out or a `pipeline()` per-item stage) over one shared static payload: put the shared payload first (tagged, e.g. `<diff>`/`<target>`), the small per-call variable token last - a variable token placed before a shared payload breaks Anthropic's cache-prefix match for every call in the fan-out. Found live as an anti-pattern (lens name interpolated first, shared payload after) in `code-review`'s `reviewPrompt`, `security-audit`'s `auditPrompt`, and `tenant-isolation-audit`'s `auditPrompt` - all three fixed, right next to their own `verifyPrompt` sibling functions which already used the correct ordering. This pass only checked the three flagship scope->lens->verify->report-shaped workflows; a future run could grep the remaining workflow scripts for the same per-lens/per-item-over-shared-payload shape and apply the same fix where found.
- `schema-lint/` (repo-internal tool, not a workflow package) is a deterministic, no-LLM static checker for the JSON Schema literals every workflow passes to `agent(..., { schema })` - `node schema-lint/schema-lint.mjs --all` catches structural schema bugs (a `required` field not in `properties`, an unknown `type`) and enforces `SCHEMA_DESIGN.md`'s enum-description rule as a WARN, both without spending a real `agent()` call. It found 0 structural bugs and 101 enum fields across 27 packages still missing a `SCHEMA_DESIGN.md` description on a real run against the whole library. It lives outside `scripts/` deliberately (that directory is Edit/Write-denied to agents in `.claude/settings.json`) - see `schema-lint/README.md`. A future run could retrofit `SCHEMA_DESIGN.md` descriptions into those 101 fields using this tool's output as the worklist, or a human maintainer could decide to fold its checks into `scripts/validate-workflow.mjs` and promote the WARN to a FAIL once the count reaches zero.
- `NULL_SAFETY_AFTER_FANOUT.md` documents a rule for `await parallel(...)`/`await pipeline(...)` results: a failed lane resolves to `null` rather than throwing, so any downstream property read must go through `.filter(Boolean)` (droppable lane) or an explicit `if (!x) throw` guard naming the failed lane (required lane), never an unguarded read. An audit of all 30 `parallel()`/`pipeline()` call sites across the repo's 17 non-archive workflow packages found 29 already correct and one real bug: `dependency-upgrade.js`'s destructured `const [breaking, security] = await parallel([...])` read `breaking.riskLevel`/`security.recommendation` unguarded two lines later, which would crash the whole run on either lane's transient failure. Fixed with a guard-and-throw. This pass only checked the top-level, non-archive packages; a future run could re-run the same audit whenever a new workflow adds a `parallel()`/`pipeline()` call, or check `archive/` if any archived package is ever revived.
- `workflow-dry-run/` (repo-internal tool, not a workflow package) is a deterministic, no-LLM dry run of a workflow script's own orchestration control flow: it mocks every `agent()`/`parallel()`/`pipeline()` call with data shaped from the real schema each call declares, makes every 3rd `agent()` call resolve `null` (simulating a transient subagent failure per the Workflow tool's own contract), and runs the real script once to see whether it degrades gracefully or crashes. `node workflow-dry-run/workflow-dry-run.mjs --all` found 3 real, previously-undocumented null-safety bugs on its first run - standalone `await agent(...)` calls (not inside any `parallel()`/`pipeline()`) whose result was read unguarded one or two lines later, in `bug-hunter` (Converge phase), `qa-suite-pro` (Implement phase), and `tdd-blueprint` (Sequence phase). All three fixed with the same guard-and-throw form `dependency-upgrade.js` established; `NULL_SAFETY_AFTER_FANOUT.md`'s rule was extended to cover standalone `agent()` calls, not just fan-out results, since the tool's own contract makes clear a single call can resolve `null` too. `--all` now passes clean (0 FAILs across all 17 packages). A future run could extend the tool to also check that every `phase()` name declared in `meta.phases` actually gets called during a dry run.
